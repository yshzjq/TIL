# 1장 2강. 수집 전 리스크 체크리스트

## 1. 기술적 접근과 이용 가능성 구분

브라우저에서 페이지가 열리거나 기술적으로 접근할 수 있다고 해서 자동 수집, 저장, 가공, 재사용까지 모두 허용되는 것은 아니다.

수집 전에 다음을 각각 확인해야 한다.

| 질문 | 의미 |
|---|---|
| 접근 가능한가? | 기술적으로 요청하고 응답받을 수 있는가? |
| 자동 수집해도 되는가? | 약관과 운영 정책에 맞는가? |
| 저장해도 되는가? | 개인정보 및 보관 조건과 맞는가? |
| 가공·공유해도 되는가? | 라이선스와 사용 목적에 맞는가? |

웹페이지를 자동 수집하기 전에는 다음과 같은 더 안정적인 경로가 있는지도 먼저 확인한다.

1. 공식 다운로드 파일
2. 공식 공공데이터 API
3. 공식 외부 서비스 API
4. RSS 또는 공개 피드

공식 API도 별도의 이용 조건이나 호출 한도가 있을 수 있다.

---

## 2. 수집 전 네 가지 위험 질문

수집 후보마다 다음 네 가지를 확인한다.

### 2-1. 이용 조건

- 이용약관을 확인했는가?
- 자동 접근 관련 규칙이 있는가?
- 저장, 가공, 재배포 조건이 있는가?
- API라면 별도의 개발자 정책이 있는가?

### 2-2. robots.txt

웹 자동 수집이라면 확인한다.

- 대상 사이트의 `/robots.txt`를 확인했는가?
- 사용 중인 `user-agent`에 적용되는 규칙은 무엇인가?
- 대상 경로가 허용 또는 제한되어 있는가?

### 2-3. 개인정보

- 이름, 전화번호, 이메일, 주소 등이 있는가?
- 여러 정보를 결합하면 개인을 알아볼 수 있는가?
- 민감하거나 사적인 내용이 포함되는가?
- 목적에 필요한 항목만 수집하는가?

### 2-4. 저작권과 라이선스

- 콘텐츠 제작자는 누구인가?
- 이용허락 또는 라이선스 표시가 있는가?
- 출처 표시나 변경 표시 조건이 있는가?
- 페이지 운영자와 콘텐츠 권리자가 같은가?

확인 결과는 다음처럼 처리한다.

```text
예
→ 근거 URL과 확인일 기록

아니요
→ 수집하지 않는 방향으로 우선 판단

불명확
→ 임의로 허용하지 않고 문의 대상으로 기록
```

---

## 3. 이용약관 확인

사이트에서 다음 항목을 먼저 찾는다.

- 이용약관
- 서비스 약관
- API 이용정책
- 개발자 정책
- 데이터 라이선스

약관에서는 다음과 같은 단어를 중심으로 확인한다.

```text
자동 / 로봇 / 크롤링 / 스크래핑
복제 / 저장 / 다운로드
가공 / 2차적 이용
재배포 / 상업적 이용
호출 제한 / rate limit
API 키 / 계정 공유
```

확인한 내용은 다음과 같이 기록한다.

| 항목 | 내용 |
|---|---|
| 문서 이름 | 확인한 정책 이름 |
| URL | 정책 문서 주소 |
| 확인일 | 조건을 확인한 날짜 |
| 관련 내용 | 필요한 조건의 짧은 요약 |
| 남은 질문 | 아직 확인하지 못한 사항 |

약관 전체를 복사하기보다 관련 위치와 짧은 요약을 남긴다.

조건은 변경될 수 있으므로 **확인일**도 함께 기록한다.

이용 조건이 불명확하면 자동 수집을 시작하지 않고 문의 및 검토 후 결정한다.

---

## 4. robots.txt

`robots.txt`는 웹 크롤러가 어떤 경로를 가져갈 수 있는지 알려주는 규칙 파일이다.

일반적으로 사이트 최상위 경로에 있다.

```python
site_origin = "https://example.org"
robots_url = site_origin + "/robots.txt"
```

예:

```text
User-agent: *
Disallow: /private/
Allow: /public/
```

의미:

```text
/private/ → 수집 제한
/public/  → 허용
```

### 주의사항

- `robots.txt`는 접근 통제나 비밀번호 장치가 아니다.
- 허용되어 있어도 저작권 이용허락을 의미하지 않는다.
- `robots.txt`에 내용이 없더라도 약관 확인은 필요하다.
- scheme, host, port가 다르면 적용 대상도 달라질 수 있다.
- `Crawl-delay`는 RFC 9309의 표준 규칙이 아니다.

## 5. 개인정보 점검

개인정보는 이름처럼 하나의 필드에만 존재하는 것이 아니다.

여러 정보의 조합으로 개인을 알아볼 수 있는 경우도 주의해야 한다.

예:

- 이름
- 전화번호
- 이메일
- 주소
- 계정 ID와 활동 기록
- 얼굴
- 음성
- 차량번호
- 건강·금융·상담 내용

다음 상황에서는 자동 수집을 멈추고 검토를 요청한다.

- 공개된 개인 연락처를 대량 수집하려는 경우
- 원래 목적과 다른 용도로 사용하려는 경우
- 보관 기간이나 삭제 기준을 설명할 수 없는 경우
- 필요하지 않은 개인 식별자를 저장하는 경우
- 민감한 내용이 포함될 수 있는 경우

### 최소 수집 원칙

> 목적에 꼭 필요한 필드만 수집한다.

필요하지 않은 정보를 “나중에 사용할 수도 있다”는 이유로 저장하지 않는다.

## 6. 저작권과 라이선스

웹에서 무료로 볼 수 있다는 것과 자유롭게 복제·가공·배포할 수 있다는 것은 다르다.

다음 항목을 확인한다.

1. 제작자는 누구인가?
2. 권리자는 누구인가?
3. 어떤 라이선스가 있는가?
4. 출처 표시나 변경 표시 조건은 무엇인가?
5. 계획한 저장·가공·제공 방식과 조건이 맞는가?

라이선스가 있다면 이름뿐 아니라 **버전과 원본 URL**도 기록한다.

예:

```text
CC BY 4.0
CC BY-NC 4.0
```

라이선스 표시가 없다고 해서 자유롭게 사용할 수 있다고 판단하지 않는다.

이 경우 다음을 검토한다.

- 사용하지 않기
- 링크만 제공하기
- 권리자에게 문의하기
- 조건이 명확한 다른 자료 찾기

기관 페이지 안의 사진이나 도표도 제3자 자료일 수 있으므로 개별 `credit`, `rights` 표시도 확인한다.

## 7. 가능 / 주의 / 제외 판단

| 상태 | 의미 | 다음 행동 |
|---|---|---|
| 가능 | 확인한 범위에서 조건과 계획이 맞음 | 작은 표본부터 검증 |
| 주의 | 확인하지 못한 조건이 있음 | 문의 및 검토 후 재판단 |
| 제외 | 개인정보 등 명확한 중단 사유가 있음 | 수집하지 않고 대안 탐색 |

`가능`은 영구적인 보장이 아니다.

수집 범위나 이용 목적이 바뀌면 다시 확인해야 한다.

판단할 때는 단순히

```text
문제없어 보임
```

이라고 적기보다, **무엇을 언제 확인했고 무엇이 남아 있는지** 기록한다.

## 8. 출처 기록

최소한 다음 정보를 기록한다.

| 필드 | 의미 |
|---|---|
| `source_name` | 제공기관 또는 서비스 |
| `source_url` | 원본 페이지 또는 API 문서 |
| `checked_at` | 이용 조건을 확인한 날짜 |
| `collected_at` | 데이터를 실제 수집한 시각 |
| `terms_url` | 이용약관 또는 라이선스 URL |
| `review_note` | 확인 결과와 남은 질문 |

예:

```python
source_record = {
    "source_name": "가상 공공 API",
    "source_url": "https://example.org/api/docs",
    "checked_at": "2026-07-16",
    "collected_at": None,
    "terms_url": "https://example.org/policy",
    "review_note": "재배포 가능 범위는 문의 중",
}
```

`checked_at`과 `collected_at`은 구분한다.

```text
checked_at
→ 이용 조건을 확인한 시점

collected_at
→ 데이터를 실제로 받은 시점
```

아직 데이터를 수집하지 않았다면 `collected_at`은 `None`으로 둘 수 있다.

## 9. Python으로 위험 분류하기

수집 후보를 딕셔너리로 표현할 수 있다.

```python
candidate = {
    "name": "공공 API",
    "collection_method": "official_api",
    "is_web_scraping": False,
    "terms_checked": True,
    "robots_checked": False,
    "personal_data": False,
    "reuse_permission_clear": True,
    "official_api_available": True,
}
```

판단 순서는 다음과 같다.

```text
개인정보 가능성 있음
→ 제외

이용약관 또는 재사용 조건 불명확
→ 주의

웹 자동 수집인데 robots.txt 미확인
→ 주의

확인 항목에 문제 없음
→ 가능
```

공식 API가 있다는 사실은 위험 자체가 아니라 더 안정적인 경로를 알려주는 정보로 사용한다.

이 분류는 법적인 결론을 내리는 것이 아니라 **확인하지 못한 항목을 드러내기 위한 도구**이다.

## 10. Playwright 사용 전 확인

Playwright = 실제 웹 브라우저를 코드로 자동 조작하는 도구

Playwright는 브라우저를 자동으로 조작해서, 화면에 나타난 데이터를 가져오는 용도

일부 웹페이지는 JavaScript가 실행된 뒤에 내용이 나타날 수 있으며, 이런 경우 Playwright 같은 브라우저 자동화 도구를 사용할 수 있다.

하지만 먼저 다음을 확인한다.

- 공식 파일이나 API가 없는가?
- 약관과 robots.txt를 확인했는가?
- 로그인이나 접근 통제를 우회하지 않는가?
- 브라우저 실행 비용을 감당할 수 있는가?
- 화면 구조 변경을 어떻게 확인할 것인가?

동적 페이지라고 해서 바로 브라우저 자동화를 선택하지 않는다.

## 11. 핵심 정리

```text
기술적으로 접근 가능
≠
자동 수집·저장·가공·재사용 가능
```

수집 전에는 각각 확인한다.

```text
이용약관
robots.txt
개인정보
저작권·라이선스
```

판단 결과는 다음처럼 기록한다.

```text
가능
주의
제외
```

그리고 반드시 함께 남긴다.

```text
근거
다음 행동
출처 URL
조건 확인일
실제 수집 시각
```

확인하지 못한 항목은 임의로 허용으로 판단하지 않고, 불명확하거나 민감한 경우 수집을 멈추고 담당자에게 확인한다.
